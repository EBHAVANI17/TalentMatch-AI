# Developer guide

## Quick start (no Docker, SQLite)

```bash
cd backend
python -m venv .venv                    # project-local environment (git-ignored), Python 3.11+
.venv/Scripts/python -m pip install -r requirements-dev.txt     # macOS/Linux: .venv/bin/python
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
```

Use the `.venv` interpreter for every backend command below (`python` in the examples means it).
The Playwright config also starts the backend with `backend/.venv`; override with `E2E_PYTHON`.

Open http://localhost:8000 (app) and http://localhost:8000/docs (API docs).
On first start the app creates `backend/data/talentmatch_production.db`, applies migrations
and (with `DEMO_MODE=true`, the default) loads demo personas.

## New web app (web/, React + TypeScript + Vite)

The new workspace is being built screen by screen next to the classic UI.

| URL | What |
|-----|------|
| `/` | Classic UI (`frontend/index.html`), still the main workspace |
| `/app` | New workspace (`web/`): sign-in and account pages, Dashboard, Jobs, Talent Match, Candidates, Search, My profile, Jobs for you, Team |

Both share the same session (`nexus-token` in localStorage), so you can move between them.

```bash
cd web
npm install
npm run dev          # http://localhost:5173/app/  (proxies /api to :8000; start the API too)
npm run build        # outputs web/dist, which FastAPI serves at /app
npm test             # Vitest unit/component tests
npm run e2e          # Playwright: starts its own API on a fresh demo DB (run `npm run build` first)
npm run gen:api      # regenerate src/lib/api/schema.d.ts after changing backend schemas
```

Conventions:
- One feature per folder in `src/features/<feature>/` (page, components, tests).
- Shared UI in `src/components/ui`. Use these instead of styling raw elements.
- All API calls go through `api()` in `src/lib/api/client.ts` (auth header, token refresh, error messages).
- Colours come from tokens in `src/styles/tokens.css` (light/dark). Never hard-code colours.
- No emojis; icons come from `lucide-react`.
- When a screen moves here, add it to `src/app/navigation.ts` and keep the classic screen until the new one is confirmed.

## Full stack with Docker (PostgreSQL + Redis)

```bash
cp .env.example .env          # then edit values
docker compose up --build
```

| Service  | Host port (override with env var)   |
|----------|-------------------------------------|
| API      | 8000 (`API_HOST_PORT`)              |
| Postgres | 5433 (`POSTGRES_HOST_PORT`)         |
| Redis    | 6379 (`REDIS_HOST_PORT`)            |

Postgres is published on **5433** so it doesn't clash with a locally installed PostgreSQL.
The image is `pgvector/pgvector:pg16`; `infra/postgres/init.sql` enables `vector` and
`pg_trgm` and creates a `talentmatch_test` database for the test suite.

To run the local (non-Docker) API against the Docker database:

```bash
DATABASE_URL=postgresql+psycopg://talentmatch:talentmatch@localhost:5433/talentmatch uvicorn app.main:app --reload
```

## Tests

From the repository root:

```bash
python -m pytest                       # throwaway SQLite database
TEST_DATABASE_URL=postgresql+psycopg://talentmatch:talentmatch@localhost:5433/talentmatch_test python -m pytest
```

Tests never touch `backend/data/`. Run both variants before merging: SQLite does not enforce
foreign keys, so some bugs only show up on Postgres.

## Database migrations (Alembic)

Migrations run automatically on startup (`AUTO_MIGRATE=true`). Manual commands, from `backend/`:

```bash
python -m alembic upgrade head                          # apply
python -m alembic revision --autogenerate -m "add x"    # create after editing models
python -m alembic check                                 # fail if models and migrations differ
python -m app.db.seed                                   # load demo data into an empty DB
```

Rules:
- Never edit a migration that has already been merged; add a new one.
- Additive changes only (new tables/nullable columns, backfill, then switch code).
- Review autogenerated files before committing; SQLite uses batch mode for ALTERs.

A database created before migrations existed is detected on startup and stamped at the
baseline revision (`0001`), so its data is kept.

## Configuration

All settings are in `backend/app/core/config.py` and come from environment variables or `.env`
(see `.env.example`). With `ENVIRONMENT=staging|production` the app refuses to start if
`JWT_SECRET_KEY` is weak, `DATA_ENCRYPTION_KEYS` is unset, `DEMO_MODE` is on, or `CORS_ORIGINS`
contains `*`.

## Security model (summary)

- Every route except login/sign-up, the public job board and `/config/public` needs a bearer token.
- Visibility rules live in `backend/app/core/tenancy.py`. Use its `scope_*` and `get_visible_*` helpers
  in routers instead of writing your own checks. Records outside the caller's tenant return 404.
- `tests/test_tenancy.py` is the cross-tenant suite. Add a case for every new tenant-owned endpoint.
- Refresh tokens rotate and are single-use; replaying one ends all of that user's sessions.
- Rate limits: `RATE_LIMIT_DEFAULT` per IP on `/api`, `RATE_LIMIT_AUTH` on login/sign-up/reset.
- Suspending a user (super-admin console) revokes their refresh tokens; their access token stops
  working immediately because `get_current_user` checks `is_active`.

## Field encryption

Candidate phone, `raw_resume_text` and `resume_versions.extracted_text` are encrypted at rest
(`backend/app/core/crypto.py`, Fernet). Models declare them as `EncryptedString`/`EncryptedText`;
application code reads and writes plaintext as usual. Stored values look like `enc::<token>`.

- Keys: `DATA_ENCRYPTION_KEYS`, comma-separated, newest first. Generate one with
  `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.
  Without it, development uses a key derived from `JWT_SECRET_KEY`; production refuses to start.
- Rotation: put the new key first (keep the old ones), restart, run `python -m app.db.rotate_encryption`,
  then remove the old keys.
- Losing the keys means losing that data. Store them in AWS Secrets Manager, separately from backups.
- A wrong key raises `DecryptionError` (never silently returns ciphertext).
- Encrypted columns can't be searched with SQL `LIKE`; search and matching use embeddings and the
  normalized skill tables instead. To encrypt a new column, change its type and add a migration like
  `0008` that widens it (ciphertext is ~4x longer) and encrypts existing rows.

## Events and background work

Changes that other parts of the system care about are recorded as **domain events** in the
`events_outbox` table, in the same transaction as the change (`app.events.emit`). Handlers in
`app/events/handlers.py` react to them (today: notifications).

- `EVENT_DISPATCH_MODE=inline` (default): events are delivered right after the request commits.
- `EVENT_DISPATCH_MODE=worker` (Docker/production): run `python -m app.workers.outbox` alongside
  the API (the `worker` service in docker-compose). Failed deliveries retry up to 5 times.

Handlers must be idempotent: an event can be delivered more than once.

Event names so far: `job.created|updated|published|paused|closed|archived`,
`application.created`, `application.stage_changed`, `candidate.created|updated|note_added`.

## File storage

Uploaded files go through `app/adapters/storage` (`STORAGE_BACKEND=local` or `s3`). Only metadata
is stored in the `documents` table. Downloads use short-lived links from
`POST /api/v1/documents/{id}/download-url`. Resume files follow the same rule as contact details:
an organization can open them only for candidates who applied to it or that it added.

## Hiring pipeline

Default stages: Applied, Screening, Shortlisted, Interview, Selected, Hired, Rejected. Organization
admins can customize them (`PUT /api/v1/pipeline/stages`). Older names (AI Screened, Interviewing,
Assessment, Offered) are accepted as aliases.

## Matching and search

Code lives in `backend/app/matching/` (engine, ontology, embeddings, redaction) and `backend/app/search/`.

- **Engine** (`matching/engine.py`): pure functions over `CandidateFacts`/`JobFacts`, which
  deliberately contain no names, contact details, photos, age or gender. Ten factors, each with a
  score, a weight and a reason; factors without data are excluded and the remaining weights
  renormalized. The total is exactly the weighted sum that the UI shows. Bump `ENGINE_VERSION` when
  scoring logic changes so stored matches are recomputed.
- **Weights**: platform defaults in `DEFAULT_WEIGHTS`; organizations override them with
  `PUT /api/v1/matching/weights`.
- **Skill ontology** (`db/reference_data.py`): catalog skills, synonyms and directional related-skill
  credit. Loaded on every startup (insert-only). Edit there, or add rows to `skill_aliases` /
  `skill_relations`.
- **Embeddings**: `EMBEDDING_PROVIDER=fastembed` (local model `BAAI/bge-small-en-v1.5`, 384-d, cached
  in `backend/.cache/fastembed`, baked into the Docker image) or `hashing` (tests/offline). Text is
  passed through `matching/redaction.py` first. Vectors refresh through events; unchanged text is skipped.
- **Stored matches**: `matches` rows are recomputed only when their `inputs_hash` changes (profile,
  job, embeddings, weights or engine version).
- **Search**: `GET /api/v1/search?q=` parses experience, location, work mode and skills from plain
  language (`interpreted` in the response), then fuses semantic, skill and keyword rankings within the
  caller's tenant scope.

Run the real-model test with `RUN_MODEL_TESTS=1 python -m pytest tests/test_embeddings.py` (downloads ~70 MB once).

## AI features (resume parsing, job drafting)

Code: `backend/app/adapters/llm/` (provider clients and `LLMRouter`), `backend/app/ai/` (orchestrator,
prompts, rule-based fallbacks), routers `api/ai_features.py` (`/api/v1/ai/...`) and `api/ai_admin.py`
(`/api/v1/admin/ai/...`).

- **Providers**: set any of `GROQ_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY` in `.env` (free tiers
  work). They are tried in `LLM_PROVIDER_ORDER`; a provider that rate-limits or fails is skipped for
  `LLM_COOLDOWN_SECONDS`. Other keys in your environment (e.g. `OPENAI_API_KEY`) are ignored.
- **No keys**: every feature still works using deterministic fallbacks in `ai/rules.py`; responses say
  which path was used (`method`: `ai` or `rules`, plus `provider` and a `notice`), and the UI labels AI output so users review it before saving.
- **Privacy**: names, emails, phone numbers and links are removed (`matching/redaction.py`) before any
  text is sent to a provider. Resume outputs (personal data) are never stored in the governance log.
- **Prompts**: versioned in the `prompt_templates` table (defaults in `ai/prompts.py`). Super admins can
  add a version and activate or roll back via `/api/v1/admin/ai/prompts`.
- **Governance**: every call is written to `ai_requests` (feature, provider, model, prompt version,
  latency, tokens, status). Model output must validate against a Pydantic schema; one retry, then the
  fallback. Limits: `AI_USER_DAILY_LIMIT` per user and the organization's monthly AI credits.
- **Tests** never call real providers: `tests/conftest.py` and `backend/scripts/e2e_server.py` blank the
  keys, and provider behaviour is tested with mocked HTTP.

## Recruiter copilot

Code: `backend/app/copilot/` (tools, references, rules fallback, service), router `api/copilot.py`
(`/api/v1/copilot/...`), web `web/src/features/copilot/` (header panel, Ctrl/Cmd+J, and `/copilot` with history).

- **Flow per question**: names of candidates the user can see are swapped for references (`[C1]`), then
  emails/phones/links are redacted; a planner call picks up to three read-only tools; the tools run inside
  the user's organization; an answer call writes a reply citing only the records found. Each question makes
  two governed AI calls (`copilot_plan`, `copilot_answer`), so it counts twice toward `AI_USER_DAILY_LIMIT`.
- **Grounding**: records go to the model in a fenced data block; references the model invents are removed
  before saving. Without AI keys, keyword routing and templated answers are used (`copilot/rules.py`).
- **Tools** (`copilot/tools.py`): candidate search, top matches for a job, jobs, pipeline summary, candidate
  overview, upcoming interviews. To add one: write a scoped function that adds `Record`s (facts only, no
  names or contact details), register it in `TOOLS`, describe it in `TOOL_GUIDE`, and add a rules route
  and a tenancy test.
- **Storage**: conversations are private to their owner; messages are stored in reference form and
  encrypted. Labels and links are resolved when read, through the tenancy rules.
- **Access**: recruiters, hiring managers and org admins (`candidates:search_pool`). Rate limit:
  `RATE_LIMIT_COPILOT`. Read-only for now; actions with approval come with agents (Phase 7).

## Organizations, memberships and switching

- A person can belong to several organizations with a different role in each (`memberships`). Platform
  roles (`SUPER_ADMIN`, `CANDIDATE`) stay on `users.role` and hold no memberships.
- The access token carries `active_org_id`. `core/tenancy.py` loads the user, the active membership and the
  organization in one query on every request, so a revoked membership stops working immediately. Tokens
  without `active_org_id` (the classic workspace) use the user's default organization.
- `POST /auth/switch-org` issues a new token pair for another organization; refresh keeps the active one.
  `GET /me/organizations` lists the caller's memberships. The web app sends `X-Org-Id`; non-GET requests
  whose header doesn't match the token's organization get 409 (another tab switched).
- `users.organization_id` / `users.role` mirror the default membership and are written only by
  `services/membership_service.py`. `tests/test_membership_guard.py` fails if other code reads them without a
  `# membership-guard: ok (<reason>)` marker.
- Hierarchy is one level: a `parent` organization has `client` organizations. Parent admins
  (`org:manage_clients`) can create clients and manage a client's memberships only while the client has
  `allow_parent_access`; this never grants access to the client's data. Every such change is audited.
- Rules: the last active admin can't be removed, suspended or demoted (409); seats are per organization
  (active memberships + pending invitations); organizations are soft-deleted (`status = deleted`).
- Existing accounts accept invitations while signed in as the invited, verified email.
