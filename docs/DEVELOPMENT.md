# Developer guide

## Quick start (no Docker, SQLite)

```bash
cd backend
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

Open http://localhost:8000 (app) and http://localhost:8000/docs (API docs).
On first start the app creates `backend/data/talentmatch_production.db`, applies migrations
and (with `DEMO_MODE=true`, the default) loads demo personas.

## Full stack with Docker (PostgreSQL + Redis)

```bash
cp .env.example .env          # then edit values
docker compose up --build
```

| Service  | Host port (override with env var)   |
|----------|-------------------------------------|
| API      | 8000 (`API_HOST_PORT`)              |
| Postgres | 5433 (`POSTGRES_HOST_PORT`)         |
| Redis    | 6379 (`REDIS_HOST_PORT`)            |

Postgres is published on **5433** so it doesn't clash with a locally installed PostgreSQL.
The image is `pgvector/pgvector:pg16`; `infra/postgres/init.sql` enables `vector` and
`pg_trgm` and creates a `talentmatch_test` database for the test suite.

To run the local (non-Docker) API against the Docker database:

```bash
DATABASE_URL=postgresql+psycopg://talentmatch:talentmatch@localhost:5433/talentmatch uvicorn app.main:app --reload
```

## Tests

From the repository root:

```bash
python -m pytest                       # throwaway SQLite database
TEST_DATABASE_URL=postgresql+psycopg://talentmatch:talentmatch@localhost:5433/talentmatch_test python -m pytest
```

Tests never touch `backend/data/`. Run both variants before merging: SQLite does not enforce
foreign keys, so some bugs only show up on Postgres.

## Database migrations (Alembic)

Migrations run automatically on startup (`AUTO_MIGRATE=true`). Manual commands, from `backend/`:

```bash
python -m alembic upgrade head                          # apply
python -m alembic revision --autogenerate -m "add x"    # create after editing models
python -m alembic check                                 # fail if models and migrations differ
python -m app.db.seed                                   # load demo data into an empty DB
```

Rules:
- Never edit a migration that has already been merged; add a new one.
- Additive changes only (new tables/nullable columns, backfill, then switch code).
- Review autogenerated files before committing; SQLite uses batch mode for ALTERs.

A database created before migrations existed is detected on startup and stamped at the
baseline revision (`0001`), so its data is kept.

## Configuration

All settings are in `backend/app/core/config.py` and come from environment variables or `.env`
(see `.env.example`). With `ENVIRONMENT=staging|production` the app refuses to start if
`JWT_SECRET_KEY` is weak, `DEMO_MODE` is on, or `CORS_ORIGINS` contains `*`.

## Project layout (current)

```
backend/
  app/
    api/        REST routers (mounted under /api/v1)
    core/       config, database, security
    db/         migrations runner, demo seed
    models/     SQLAlchemy models, Pydantic schemas
    services/   business logic (matching, AI copilot, analytics, audit, notifications)
  alembic/      migration scripts
frontend/       legacy single-page UI (index.html), being migrated to web/
tests/          pytest suite (conftest.py sets up the isolated DB)
infra/          Docker/Postgres setup (AWS Terraform comes later)
```
